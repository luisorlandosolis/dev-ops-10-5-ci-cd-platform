# Architectural Decisions

## ADR-001: Jenkins Hosted on Kubernetes

### Status

Accepted

### Decision

Deploy Jenkins as a Kubernetes workload rather than a standalone virtual machine.

### Rationale

The Kubernetes platform already existed as a strategic platform engineering initiative and provided:

- Workload orchestration
- Declarative management
- Simplified upgrades
- Persistent storage integration
- Future dynamic build agent capabilities

### Outcome

Jenkins was successfully deployed and operated within Kubernetes and became the foundation of the Dev-Ops-10.5 CI/CD Platform.

## ADR-002: SMB CSI Persistent Storage

### Status

Accepted

### Decision

Use SMB CSI backed Persistent Volumes and Persistent Volume Claims for Jenkins persistent storage.

### Rationale

Requirements included:

- Persistent Jenkins configuration
- Job history retention
- Plugin retention
- Recovery after pod recreation
- Shared storage capabilities

The existing storage environment already provided a resilient SMB-based storage platform.

### Outcome

Jenkins configuration, jobs, plugins, credentials, and build history persist across Kubernetes pod recreations and platform maintenance activities.

## ADR-003: HTTPS Access Through NGINX Ingress

### Status

Accepted

### Decision

Publish Jenkins through HTTPS using NGINX Ingress.

### Rationale

The platform required:

- Secure administrative access
- Browser trust validation
- Encrypted traffic
- Consistency with Kubernetes ingress architecture

### Outcome

Jenkins management and user traffic are encrypted and accessible through the platform ingress architecture.

## ADR-005: Pipeline-as-Code

### Status

Accepted

### Decision

Store Jenkins pipelines in source control using Jenkinsfiles rather than maintaining pipeline definitions directly inside Jenkins.

### Rationale

Benefits include:

- Version control
- Auditing
- Traceability
- Portability
- Infrastructure-as-Code alignment

### Outcome

Pipeline logic is maintained within GitHub and automatically executed by Jenkins.

## ADR-006: GitHub HTTPS Authentication

### Status

Accepted

### Decision

Use Fine-Grained Personal Access Tokens with HTTPS authentication for GitHub integration.

### Rationale

Initial implementation attempted GitHub Deploy Keys and SSH authentication.

Testing revealed an interaction between SMB-backed storage and temporary SSH key permissions generated by Jenkins.

The Jenkins temporary key files could not satisfy OpenSSH private key permission requirements when stored on the SMB-backed filesystem.

### Outcome

GitHub HTTPS authentication using Fine-Grained Personal Access Tokens was successfully validated and became the operational authentication method.

### Lessons Learned

Not all storage platforms behave identically with temporary SSH private key generation workflows.

Authentication methods should be evaluated in the context of the underlying storage architecture.

## ADR-007: Poll SCM for Automated Build Triggers

### Status

Accepted

### Decision

Use Jenkins Poll SCM automation for repository change detection.

### Rationale

Initial GitHub webhook testing was unsuccessful because Jenkins was hosted exclusively on private internal infrastructure and was not reachable from the public Internet.

Poll SCM provides automated build triggering without exposing Jenkins externally.

### Outcome

Automated build execution was successfully validated using repository polling.

Workflow:

Git Commit
→ Git Push
→ GitHub
→ Poll SCM
→ Jenkins
→ Automated Build

## ADR-008: Controller-Based Build Execution (Initial Phase)

### Status

Accepted

### Decision

Initial pipeline validation will execute directly on the Jenkins controller.

### Rationale

Controller-based execution simplifies:

- Platform deployment
- Integration testing
- Authentication validation
- Pipeline development

This approach allows validation of the CI/CD platform before introducing additional agent complexity.

### Outcome

Multi-stage pipelines were successfully executed and validated.
